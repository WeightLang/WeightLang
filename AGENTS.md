# Storage

- Follow [docs/storage.md](docs/storage.md). Keep complete models in `weights/<model>/` and retained experiment baselines, candidates and reports in `weights/<experiment>/`; never overwrite without explicit `--force` or treat them as cache.
- Small temporary files belong in `/tmp/weightlang/` (platform equivalent elsewhere). Large weights, datasets, downloads and build intermediates use disk-backed project paths or `.cache/weightlang/`, never tmpfs; check space and the actual mount before large writes. `target/` is only a Rust compiler cache.
- Clean only task-created disposable files; preserve unrelated work and model outputs. Other projects use `/tmp/<project>/` and their own disk cache.

# Language changes

- The source language targets Rust edition 2024 for host integration and Rust API examples. For every public WGT language change, update [docs/reference.zh-CN.md](docs/reference.zh-CN.md), related topic docs and WGT skill references/examples in the same change. This includes parser/version rules, expressions, defaults, shape/dtype contracts, graph/loop/runtime behavior, training/import/freezing and `std/*.wgt` changes.
- Treat `crates/wgt-language/src/`, `language/primitive_specs.json`, `std/*.wgt` and relevant `crates/wgtime-core/` and service code as authoritative for implemented language and execution. Rust applications own native WGT data preparation, I/O, scheduling, service connection and training loops; WGT and `std/` focus on reusable model architecture and model-internal parameter/tensor flow, submodules, branching, loops and state, plus optional differentiable loss. The legacy general-purpose WGT host-script architecture is being retired: do not create new WGT host-control scripts or document that architecture as a supported direction. Do not claim old implementations have been removed unless verified. Document execution and import support separately for the Rust/service backend and Python SDK, using each backend's implementation and behavioral tests. Document purpose, complete signatures, parameters/defaults, constraints, versions, limitations and valid examples. Distinguish definitions, initialized instances, trained weights, local implementation and released features; parsing alone does not prove execution support.
- Compare the reference against all `_stmt_*` handlers, operator sets/defaults and standard-library signatures. Report unverified items; no remote CI is required for documentation maintenance. Do this as part of the task, not with a background generator.

# WGT authoring

- The WGT model source entrypoint must be named `model.wgt`. Put each independent model/example in its own directory (for example `examples/native_training/working_memory/model.wgt`); use directory names to distinguish models, never `main.wgt`, `train.wgt` or a feature-named entrypoint. Keep commands, links, test fixtures that load real examples, and relative data/output paths aligned when moving files. This source-entry convention does not rename artifact snapshots such as `source.wgt` or library modules under `std/`. PyTorch starter recipes use their TOML configuration and Python host file; do not add an unused `model.wgt` to imply a WGT compiler path.

- For model authoring or language implementation, use `/home/lightjunction/.codex/skills/wgt-development/SKILL.md` when available. Keep its grammar and runnable examples aligned with the latest implemented language only; validate against the current parser/runtime, excluding historical syntax and unimplemented proposals.
- New or substantially changed WGT examples need meaningful comments explaining axis meanings, shape transitions, gate/reduction intent, independent versus shared loop weights and initialization/training state. Explain intent rather than narrating obvious lines.

# Architectural boundary

- Python and Rust applications own data preparation, I/O, scheduling and training loops. WGT and `std/` focus on reusable model architecture and model-internal parameter/tensor flow, submodules, branching, loops and state, plus optional differentiable loss. The legacy general-purpose WGT host-script architecture is being retired; do not create new WGT host-control scripts or present it as a supported direction. See docs/python-sdk.md for the PyTorch target, docs/native-backend.md for the Rust model contract and docs/native-training.md for native implementation status.
- The Python SDK lives in `python/`. Reuse `wgt compile --target torch` and the existing Rust frontend for WGT parsing, imports and static tensor contracts; never create a second parser. Lower supported pure-forward graphs to ordinary PyTorch modules/FX graphs and use standard autograd, optimizers, data loaders and visualization tools. Explicitly reject unsupported semantics, including mutable state, dynamic control flow and constrained learn parameters. Keep native checking, packaging and execution independent of Python.
- Optional PyTorch starter recipes remain ordinary Python host programs copied by `wgt init`. Reuse uv for Python selection, isolated environments, dependency resolution and `uv.lock`; reuse PyTorch and Transformers for computation, optimization and generation. Keep WeightLang project/model/runtime/train/infer/python.runner settings in `wgt.toml`; keep Python metadata, dependencies and uv settings in `pyproject.toml`, and Rust build/dependency settings in `Cargo.toml`. The current tiny-lm/MLP recipes define their architecture in TOML/Python; WGT source imports use the separate SDK entrypoints.
- Select one complete WeightLang configuration per project. Legacy `wgt.mod` and embedded `[tool.wgt]` in `pyproject.toml` remain compatible alternatives; reject multiple WGT sources rather than merging fields. An ordinary Python/uv `pyproject.toml` can coexist with `wgt.toml`. New Python starters generate both files, and migration removes the `tool.wgt` prefix while preserving all Python/uv settings.
- CLI-launched Python hosts receive the selected configuration's absolute path in `WGT_CONFIG_FILE`. Template data and output paths are relative to that configuration's directory; explicit CLI values override file values, followed by defaults for optional settings. Custom runners must update their configuration loading when moving from embedded `[tool.wgt]` to `wgt.toml`. Keep the execution boundary explicit: current `wgt train`/`infer` dispatch Python runners; a general Rust/Python training scheduler is not implemented by unifying configuration.
- SDK `load`/`loads`/`from_ir` use their explicit source/definition and device arguments. They do not implicitly apply project train/infer/runtime settings or `WGT_CONFIG_FILE`. Source compilation retains the compiler's import and toolchain discovery rules. Hosts that use project runtime configuration must read it and pass the relevant values to SDK and PyTorch APIs.
- Model definitions, service instances, trained weights and optimizer-bearing checkpoints are distinct. Compiling a definition must not execute forward, initialize service state, train, or create artifacts implicitly. SDK load/loads/from_ir explicitly construct PyTorch modules and initialize declared parameters; save is separate. Native model execution and mutable state belong to the unique wgtime service; SDK modules and PyTorch recipes execute in their Python host process.
- Rust/service and Python SDK contracts are distinct. Verify model inputs, imports, batches, dtypes, state and cache behavior against the corresponding backend and its documented tests before claiming support; acceptance in one backend does not establish support in the other.
- Do not add arbitrary Python execution inside native WGT model computation or native Rust host paths as a shortcut.
