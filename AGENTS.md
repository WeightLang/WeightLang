# Storage

- Follow [docs/storage.md](docs/storage.md). Keep complete models in `weights/<model>/` and retained experiment baselines, candidates and reports in `weights/<experiment>/`; never overwrite without explicit `--force` or treat them as cache.
- Small temporary files belong in `/tmp/weightlang/` (platform equivalent elsewhere). Large weights, datasets, downloads and build intermediates use disk-backed project paths or `.cache/weightlang/`, never tmpfs; check space and the actual mount before large writes. `target/` is only a Rust compiler cache.
- Clean only task-created disposable files; preserve unrelated work and model outputs. Other projects use `/tmp/<project>/` and their own disk cache.

This includes parser/version rules, expressions, defaults, shape/dtype contracts, graph/loop/runtime behavior, training/import/freezing and `std/*.wgt` changes.

Document purpose, complete signatures, parameters/defaults, constraints, versions, limitations and valid examples. # WGT authoring

- The WGT model source entrypoint must be named `model.wgt`. Put each independent model/example in its own directory (for example `examples/native_training/working_memory/model.wgt`); use directory names to distinguish models, never `main.wgt`, `train.wgt` or a feature-named entrypoint. Keep commands, links, test fixtures that load real examples, and relative data/output paths aligned when moving files. This source-entry convention does not rename artifact snapshots such as `source.wgt` or library modules under `std/`. PyTorch starter recipes use their TOML configuration and Python host file; do not add an unused `model.wgt` to imply a WGT compiler path.

- For model authoring or language implementation, use `/home/lightjunction/.codex/skills/wgt-development/SKILL.md` when available. Keep its grammar and runnable examples aligned with the latest implemented language only; validate against the current parser/runtime, excluding historical syntax and unimplemented proposals.
- New or substantially changed WGT examples need meaningful comments explaining axis meanings, shape transitions, gate/reduction intent, independent versus shared loop weights and initialization/training state. Explain intent rather than narrating obvious lines.

# Architectural boundary

- Python and Rust applications own data preparation, I/O, scheduling and training loops. WGT and `std/` focus on reusable model architecture and model-internal parameter/tensor flow, submodules, branching, loops and state, plus optional differentiable loss. The legacy general-purpose WGT host-script architecture is being retired; do not create new WGT host-control scripts or present it as a supported direction. See docs/python-sdk.md for the PyTorch target, docs/native-backend.md for the Rust model contract and docs/native-training.md for native implementation status.
- The Python SDK lives in `python/`. Reuse `wgt compile --target torch` and the existing Rust frontend for WGT parsing, imports, initializers, submodel identities and tensor contracts; never create a second parser. Preserve the native IR's forward, gradient, control-flow, learn-domain and transaction rules. Pure tensor models use FX; dynamic programs use ordinary PyTorch modules. Typed operations retain their native no-autograd contract. Use standard optimizers with `bind_optimizer` for post-step learn projection. Keep native checking, packaging and execution independent of Python. Differential tests use the native `torch_reference` example, never a second Python implementation as their only oracle.
- Optional PyTorch starter recipes remain ordinary Python host programs copied by `wgt init`. Reuse uv for Python selection, isolated environments, dependency resolution and `uv.lock`; reuse PyTorch and Transformers for computation, optimization and generation. Keep project configuration in standard `pyproject.toml`, with WeightLang settings under `[tool.wgt]`. The current tiny-lm/MLP recipes define their architecture in TOML/Python; WGT source imports use the separate SDK entrypoints.
- Model definitions, service instances, trained weights and optimizer-bearing checkpoints are distinct. Compiling a definition must not execute forward, initialize service state, train, or create artifacts implicitly. SDK load/loads/from_ir explicitly construct PyTorch modules and materialize declared parameters and state; save is separate. Native model execution and mutable state belong to the unique wgtime service; SDK modules own their PyTorch state in the Python host. SDK checkpoints include registered state buffers; native parameter-only weight artifacts retain their own contract.
- The shared frontend has sequential, forward and typed-operation model plans. Ordinary forward uses one fixed-width f32 vector; typed operations declare zero or more fixed-width inputs. Pure helper imports are resolved by the frontend. Python batches and explicit dtype/device conversion are SDK host features; verify their behavior independently of native service features, static graph capture and hardware acceleration. Do not infer untested cache, dtype or deployment support from successful parsing or graph construction.
- Do not add arbitrary Python execution inside native WGT model computation or native Rust host paths as a shortcut.
